# 功能

已构建的功能，以及已设计但尚未构建的功能。

“已构建”下的所有内容在代码库中都有代码和测试。其中任何内容都未经临床审查，也未针对照护进行验证。

## 已构建

### 患者身份

注册和搜索，带重复检查。支持合并和撤销合并。

### 可解释的匹配

纯 Rust 匹配器，为每个字段说明原因。它绝不自动链接双胞胎，并在证据缺失时拒绝匹配。

### 访问控制

角色、照护关系、同意、使用目的和“破窗”，都在服务中判定。

### 哈希链审计

每次读取和写入，都记录在受数据库触发器保护、可通过路由验证的轨迹中。

### 初始临床数据

过敏、观察、患者照片和修改请求。生命体征同时显示测量时间和写入时间。

### 死亡报告

死亡以报告的形式存储，附有来源和原因，只有人员才能确认或撤回。报告有效期间，外发事件被暂缓；死亡经确认后，代理人访问和患者本人的登录都会停止。尚无临床医生或丧亲者审阅过此功能。

### 需求与合理调整

一个人为使用医疗服务所需要的支持，例如口译员、大字印刷或无台阶通道，从固定列表中选择，并可设定再次核对的日期。它显示在横幅中，由工作人员记录，患者可以查看并更正自己的内容，也可作为 FHIR Flag 读取。它只向工作人员提供信息，本身不改变任何事情。尚无临床医生或残障人士审阅过此功能。

### 闭环转诊

带工作清单的转诊。未获回复的转诊会被标记。

### 互操作性

针对 Patient、AllergyIntolerance 和 Observation 的 FHIR R4 和 R5 读取。入站 HL7 v2 ADT 数据流，被拒绝的消息进入审查队列。

### 临床界面

采用“服务于前端的后端”的 SvelteKit：浏览器不持有令牌。十种机器撰写的语言区域。

## 已设计，尚未构建

以下每一项都有规范或研究页面，但还没有代码。

- 临床记录的大部分内容：就诊、医嘱、结果、笔记和处方
- 临床内容上的安全标签，使屏蔽能够应用于这些内容
- 由临床医生设计和重新设计的照护路径
- 急症、社区和精神卫生的场景配置，以及专科视图
- 记录的移动端布局
- 培训环境和[培训叠加层](https://github.com/electronic-patient-record/electronic-patient-record/blob/main/spec/training-overlay/index.md)
- 批量导入和 FHIR 批量导出
- 备份和恢复

请参阅这些内容背后的[研究](@/研究/)。
